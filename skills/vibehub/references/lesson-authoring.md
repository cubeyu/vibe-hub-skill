# VibeHub lesson authoring

Use this reference to design or improve a lesson when the VibeHub repository SOP is unavailable. When `site/catalog/TERM-COMMUNICATION-SOP.md` exists, follow that document as the source of truth.

## Define success first

Write one outcome in observable language:

```text
After this lesson, the learner can identify / distinguish / predict / choose / verify …
```

Add acceptance criteria that show the learner can use the concept in a real project. Avoid outcomes such as “understands X” that cannot be observed.

## Let experience come before terminology

Assume the learner can describe a desired result without knowing its formal name.

1. Begin with a recognizable behavior, problem, or consequence.
2. Let the learner compare, manipulate, predict, identify, or choose.
3. Introduce the term after the learner has experienced the distinction.
4. Reuse the term while applying the choice to the learner's project.
5. Verify understanding through the finished behavior, not vocabulary recall.

Do not ask a learner to choose between named concepts before teaching what those concepts do. When two concepts are easily confused, place both in one realistic task and make their behavioral boundary visible.

## Build one teaching line

Use one realistic task to connect:

1. A problem the learner can recognize.
2. A visual explanation of the relevant relationship or change.
3. A learner action or judgment before formal naming when possible.
4. Only the text needed to explain the term, causes, limits, and hidden behavior.
5. One exercise that requires a choice, prediction, identification, or action.
6. One realistic request the learner can give an Agent.
7. A verification step after the Agent changes the project.

Each part must teach something distinct. Remove a section if deleting it would not reduce the learner's capability.

## Choose a visual form

Match the representation to the concept:

| Concept | Prefer |
|---|---|
| UI component | Real interface, anatomy, states, variants |
| Before/after quality | Direct comparison |
| System responsibility | Flow or data path |
| Command or Git action | State before → action → state after |
| Parameter or mechanism | Change one input and observe the output |
| Confusable concepts | One shared task with boundaries marked |

Cards, colored boxes, headings, and columns are containers, not explanations. A teaching visual must reveal a relationship, sequence, state, boundary, or change.

## Design the exercise

- Test the lesson's main judgment, not trivia.
- Make the learner act before revealing feedback.
- Phrase the task in everyday language when the lesson is introducing the term.
- Derive wrong choices from realistic misunderstandings.
- Explain why the result is right or wrong immediately.
- Stop after one exercise when it already demonstrates the outcome.

## Write Agent dialogue

Keep only language a real learner would send:

- Describe the observable problem or desired result.
- Do not require the term in the learner's initial request.
- Use the newly learned term later when it improves precision.
- Ask the Agent to inspect before changing when diagnosis matters.
- Ask for an observable verification after the change.

Do not turn every example into a role/background/goal/constraints/output-format template.

## Improve existing lessons

Preserve effective visuals, interactions, examples, and copy. Improve in this order:

1. Remove repetition and meaningless content.
2. Clarify existing titles, explanations, and examples.
3. Strengthen the information carried by the existing visual.
4. Add one necessary judgment exercise.
5. Add realistic Agent dialogue.
6. Add a new module only when the existing structure cannot carry the required outcome.

Avoid encyclopedic detail. Include enough mechanism and boundaries for the learner to make decisions, recognize risks, communicate clearly, and verify results.
